# 实盘交易安全指南

> 当前方德期货仅开放手动交易；期货自动策略下单暂时关闭。下文点值与合约映射说明保留供后续接入。

本指南说明从回测或信号模式进入真实资金前的最低检查。交易所、券商、地区和账户类型会改变可用产品；当前产品目录和账户返回值优先于静态示例。

## 闪电交易数量换算

闪电交易按金额下单时，如果无法取得有限正数的换算价格，或无法算出有限正数的币数量，会返回 HTTP 400 拒绝本次请求。换算失败时绝不把输入的 USDT 金额当成币数量。拒绝发生在设置合约账户和提交订单之前，不会自动重试下单。有效限价和近期参考价格仍使用原有换算路径；现货明确按币数量输入的订单保留独立的数量处理路径。部署后端修复即可执行拦截，桌面端和手机端语言包更新提供翻译后的拒单提示；不需要数据库迁移。

## 券商订单数值校验

羊驼、盈透、老虎、微牛和方德在 HTTP 接口与券商适配器两层校验订单数值。必填股数、名义金额和限价必须为有限正数；未启用的可选止盈止损价格允许为零。NaN、无穷大、负数、布尔值和格式错误的数值会在本地被拒绝。羊驼限价金额换算还会拒绝溢出和取整后为零的数量。盈透括号单和羊驼附带保护单在提交主单前先校验保护参数。原有股数精度、港股整手规则和受支持的按金额下单保持生效。部署时同步更新后端及使用这些适配器的交易进程；不需要数据库迁移。

## 支持边界

| 市场 | 当前实盘通道 | 关键限制 |
| --- | --- | --- |
| Crypto | Binance、Bitget、Bybit、OKX、Gate、HTX | spot 与 swap 取决于交易所和账户能力 |
| 交易所直接股票 | Gate 股票通道 | 保留准确币种和目录标识；只做多 |
| 交易所代币化股票 | OKX、Bybit、Bitget Reality | 必须通过目录和地区可用性校验；只做多 |
| 交易所股票永续 | Binance、OKX、Bitget、Bybit、Gate | 属于衍生品；使用准确原生合约和 swap 规则 |
| Binance bStocks | Binance | 使用准确目录交易对；现货语义；不可使用杠杆 |
| USStock | Alpaca、IBKR、Tiger、Webull、方德 | 当前券商策略只做多 |
| HKStock | Tiger、方德 | 仅做多 |
| Futures | 无 | 自动策略下单暂未开放；方德仅支持手动交易 |
| 其他可解析市场 | 暂无 | 有数据或能回测不代表支持实盘 |

HTX 股票类产品在权威产品元数据和执行契约验证前拒绝。混合市场 live 不支持。完整边界和标的格式见 [Strategy API V2 开发指南第 18 节](STRATEGY_DEV_GUIDE_CN.md#18-部署与实盘边界)。

### Bitget 账户模式

Bitget 凭据默认自动识别账户模式。统一账户使用 UTA V3，经典账户或 `hybrid` 账户使用对应的经典 V2 现货与合约接口。账户处于 `switching` 或 `upgrading` 状态时会暂时禁止交易，避免迁移期间把订单发送到错误账户。自动识别不适用时，运维人员可以通过 `bitget_account_mode` 将凭据固定为 `uta` 或 `classic`。

## 上线前检查

1. **账户**：使用独立子账户或低余额账户；只授予必要交易权限，关闭提币权限。
2. **标的**：确认交易所、市场类型、结算币种、原生 symbol 和 API family。
3. **策略**：源码、manifest、方向和杠杆声明通过校验。
4. **沙箱**：使用受支持的 Linux 部署，确认策略启动时没有内核隔离或沙箱协议错误；不得通过进程内执行绕过失败。
5. **回测**：人工检查数据、费用、滑点、资金费、成交账本和最大回撤。
6. **信号**：先运行 `signal`，核对通知、频率、时区和重启后的状态恢复。
7. **仓位**：确认账户现有手工持仓和其他策略持仓；处理所有未知差额。
8. **限制**：设置名义金额、单标的、总敞口、杠杆和损失边界。
9. **应急**：确认操作者能停止部署、撤销挂单并使用紧急停止。

## 挂单网格启动

初始市价建仓前，执行器会按交易所的数量步长、最小数量和最小名义金额检查所有分配了资金的网格，使用实际逐格预算、合约杠杆、合约面值和按价格步长规范化后的进出场价格。零权重网格不参与检查；全部为零权重时拒绝启动。无法取得标的规则或存在不可交易的网格时，启动被阻止，策略日志记录对应格子的预算、请求数量和可取得的最小交易限制。系统不会自动向上凑单、增加资金或杠杆，也不会自动减少格数。

除价格越界后按配置暂停等待的情况外，没有已确认挂单的网格不能显示启动成功。恢复运行时可以保留已确认的退出挂单，无需因此新开仓。这些检查不预留保证金，也不能保证交易所最终接受订单。若初始仓位已成交，之后挂单失败，原有回滚逻辑仍负责平掉本次启动新建的仓位；回滚失败会单独报错。

## 启动与 Worker 恢复

`STRATEGY_RUNTIME_STARTUP_TIMEOUT_SECONDS` 限制启动命令等待就绪的时间，默认 900 秒、最小 60 秒，包含历史行情加载，与沙箱回调超时分开。命令退回等待后，轮询计时持续累计，即使换控制进程领取也不会重置；只有其他 Worker 接管租约已过期的执行中命令时才重新计时。修改这个环境变量后需要重启交易 Worker。

轮询运行器在首次风控或信号计算前报告就绪。启动命令退回等待状态之前，先停止该命令的心跳，避免误报租约丢失。启动最终失败后，禁止本地运行任务继续执行并请求退出；确认退出后释放所持租约，若退出超时则停止续租、等待租约过期。这一清理不提交平仓单，也不撤销券商侧订单，已有订单和持仓仍需对账。此前启动失败的策略应先部署修复，再重新启动，不要通过删除租约记录修复状态。本次修复无需数据库迁移。

## 运行中

- 监控运行状态、订单状态、成交、仓位、可用余额和通知。
- 对账发现未知差额时，系统会暂停同方向开仓或加仓；不要绕过保护。
- 最小数量、步长、最小名义金额和可用保证金可能改变最终提交数量。
- WebSocket 用于低延迟，REST 对账仍是断线后的恢复来源。
- 策略只能管理分配给自己的仓位，不能用它吸收手工或其他策略的仓位。

持仓归属校验只会对只读账户快照的临时传输故障进行重试。默认采用 0.5 秒指数退避并加入 20% 随机抖动，重试一次，可通过 `LIVE_TRADING_POSITION_SNAPSHOT_RETRIES`、`LIVE_TRADING_POSITION_SNAPSHOT_RETRY_BACKOFF_SEC` 和 `LIVE_TRADING_POSITION_SNAPSHOT_RETRY_JITTER_RATIO` 配置。所有快照尝试均失败时，开仓仍按失败关闭原则阻止，运行日志记录临时连接告警，不会假定账户为空仓。挂单网格会请求撤销并核对开仓单，但保留已经确认的退出、止损、止盈和 reduce-only 保护单。只有新鲜快照明确证明账户仓位低于策略分配或受保护分配时，才会撤销或重建退出单；快照或凭证暂时不可用不代表已经空仓。

下单采用独立且更严格的策略。超时、断线或已发送但未确认都属于结果不确定，不会直接再次提交，而是先使用持久化的客户端订单号对账。只有交易所明确返回“未受理”，且原因为限频或市场临时不可用时才会重试；默认重试一次，复用同一个稳定客户端订单号，并采用 0.5 秒指数退避和 20% 随机抖动。可通过 `LIVE_TRADING_ORDER_SAFE_RETRIES`、`LIVE_TRADING_ORDER_RETRY_BACKOFF_SEC` 和 `LIVE_TRADING_ORDER_RETRY_JITTER_RATIO` 配置。鉴权、权限、资金、数量、标的及账户模式等业务拒绝不会重试。已确认的 reduce-only 平仓残量继续使用独立的持仓对账策略。

挂单网格会在请求交易所前持久化待确认订单。结果不明确时，该网格暂停后续提交，等待对账确认，重启 worker 后也不能换新订单号重下。订单账本无法读取不等于没有订单。部分入场成交增加退出覆盖时，只补挂差额，保留已有退出单，不把合理的分批退出单误判为重复单。需要缩减过量退出单时，必须先取得新鲜仓位快照，再确认撤单并处理竞态成交。缺字段或非法仓位数据不能作为空仓证据。

普通服务器错误不代表订单未被受理。例如，[Bybit 的 `10016` 表示服务器错误](https://bybit-exchange.github.io/docs/v5/error)，[Binance 也明确部分超时响应的执行结果不确定](https://developers.binance.com/docs/derivatives/usds-margined-futures/general-info)。Gate 现货与永续订单可先使用原始自定义 `text` 标识核对，取得交易所订单号后立即保存。自定义标识查询有交易所保留期限，超期仍无法确认的订单应继续阻止重下并转人工核对，不能仅因时间过去就认定失败。上述网络故障保护不替代用户明确停止操作或真实触发的策略风控退出。

### 策略净值与共用账户

Strategy API V2 按部署的当前净值计算下单资金：配置的初始资金，加历史累计价格已实现盈亏，减已记录的交易手续费，加按收付方向记账的资金费和经纪商流水，再加策略自有持仓的浮动盈亏。停止后重新启动策略或重启 worker 不会重置这本账。运行时与页面净值采用同一累计口径；行情更新时，两者的标记价格可能短暂不同。净值不大于零时没有开仓预算。账本查询失败会使本轮计算失败并交由现有运行失败机制处理，不会回退到初始资金；这不会撤销已提交订单或自动平仓。

例如当前净值为 36.36、杠杆为 2 倍时，名义容量是 72.72，再考虑现有预算缓冲、费用及交易所限制，而不是按最初 500 的本金乘以 2。百分比目标按当前净值计算；显式指定数量仍须通过策略预算检查。正常的减仓、平仓不受开仓预算限制。

策略净盈亏按策略自身记录的成交及分摊的开平仓手续费计算。交易所订单盈亏单独展示，并保留交易所的费用口径。手动交易与策略共用交易所持仓时，交易所的持仓均价可能不同于策略成本。不能用交易所订单回报覆盖策略盈亏、净值或成本，也不能为对齐数字而将手动仓位并入策略。需要物理隔离时应使用独立账户或子账户；高级持仓归属模式保护的是数量，不能隔离交易所均价和保证金。

已经确认并保存到 `qd_exchange_order_pnl` 的订单盈亏，只要回报数量与该订单已记录的成交数量一致，就直接复用；不会因超过 5 分钟、刷新页面或重启 worker 而重新请求交易所。缺少回报或成交数量变化时，仍按现有限额核对；其他订单查询失败不会隐藏已保存且数量匹配的结果。WebSocket 成交证据也保存在 `qd_execution_events`，可用于重建回报。这些回报只用于单独展示，不覆盖策略账本。

### 平仓精度与浮动盈亏

成交数量使用十进制加减，仅吸收相对于本次平仓数量的二进制舍入误差。持仓写入时同步更新数量、价格及浮动盈亏；延迟到达的行情更新不能覆盖数量或成本已变化的记录。实盘净值指标及净值曲线按当前记录的数量、入场成本和标记价格计算浮盈，避免平仓前缓存的旧浮盈继续抬高净值。正常行情更新也会重估数量为正的精度尾数记录。这不会新增统一的小额清仓阈值，不删除历史成交，也不批量删除尾仓。

### Alpaca 碎股尾仓

使用 Alpaca 的 `USStock` 实盘策略，剩余策略持仓不超过 `0.01` 股时，全平请求不再进入订单队列，避免尾仓反复平仓并触发失败通知。阈值单位是股，不是美元；这是应用层规则，不代表券商的最小交易数量。持仓数量及其价值仍保留在账本中，跳过请求不会记为成交或将持仓清零。超过阈值的平仓、部分减仓、开仓、信号模式、其他券商和 Crypto 精度保持不变。规则不会取消已经入队的订单。

### 连续下单失败自动停止

对于不属于组合调仓批次的逐笔订单，实盘待执行订单 worker 对余额/保证金不足、凭证、交易标的和账户配置等明确拒单计数；无效的开仓数量也计入。同一次运行连续达到 5 次后自动停止。计数保存在 PostgreSQL，worker 重启不会清零；交易所新受理一笔订单才清零。进入本地队列、空闲计算周期，以及已受理订单的后续状态更新，都不算新的成功。

单向持仓模式下的反向库存保护、持仓归属冲突、只减仓冲突、小额退出单、动态价格限制、限流、临时网络故障和提交结果未确认不计入，也不清空此前的明确失败。原有致命鉴权/适配器错误立即停止的处理保持不变。

达到阈值后，将本次运行标记为停止，拦截本次运行尚未提交的队列订单，并通过持久化停止命令清理执行环境。旧运行的停止命令不会停止重新启动后的新运行。已提交交易所的订单仍需继续核对；自动停止默认不平仓。如果操作者在命令等待执行时明确选择“暂停并平仓”，则按正常平仓流程及其保护规则处理。

完成停止后生成一次站内通知，并通过策略已勾选的邮件、短信、Telegram、Discord、Webhook（含支持的聊天平台机器人）发送停机提醒。通知目标优先使用策略配置，未填写时使用用户通知设置；邮件还可回退到账户邮箱。各渠道需完成相应配置，例如邮件需要 SMTP、短信需要 Twilio。提醒包含策略和失败原因，并提示检查持仓、挂单和故障原因后手动重启。通知按运行去重、尽力投递，单个渠道失败不影响尝试其他渠道，不会反复通知或重新启动策略。

### 组合调仓批次

实时执行进程在第一笔订单入队前认领本次调仓批次。批次编号不随 worker 接管变化，已有批次不会重新打开，也不会通过更换编号绕过封口保护。重启重放只跳过重复提交，已有订单继续正常对账。如果上次在入队过程中中断，未入队部分需要核查，不自动补发历史订单。这保证的是防重复，不代表所有调仓分项都已完成；恢复路径不会删除已有订单、成交或持仓。

组合策略同一次计算中进入队列的订单共用一个持久化批次标识。订单仍异步执行，不等待通知汇总。批次入队结束后，worker 等全部已入队订单得到接单确认或终态，再按批次创建顺序判断，而不是按交易所回执先后判断。待处理或结果未知的订单不会因等待时间长而算作失败。

整批只要有订单被接收、部分成交或全部成交，就清零失败计数，即使其他标的拒单也不拖停整个组合。整批处理结束后，没有任何成功且至少有一笔计数范围内的明确拒单，才累计一次失败；连续 5 个这样的批次才停止，一批中拒单 10 笔也只算一次。只有保护性拦截的批次不计数，也不清零。逐笔失败和批次失败不会混加。已经成功执行的订单不回滚，失败记录仍保留，此规则不新增自动重试。

实盘和信号模式的组合通知均按用户、策略运行及批次汇总，每个已勾选渠道各发送一份，不再逐笔发送。结果齐全时发送；否则在入队结束满 30 秒后的首轮对账中发送状态快照。汇总区分已接单、已成交、部分成交、失败、取消和待确认，不把入队或接单写成调仓完成，也不把虚拟成交写成真实成交。短信等短消息渠道沿用现有长度限制，先展示统计，过长的明细可能截断，完整订单记录在系统内查看。后续状态不再重复触发批次通知，逐笔日志仍保留；自动停止提醒单独发送，不等待调仓汇总。

批次状态和通知领取标记保存在数据库，重启不会重复计算或通知。各渠道独立、尽力投递，单个渠道失败不影响尝试其他渠道；投递失败或发送期间进程崩溃后，不自动重发已经领取的汇总通知。投递与下单、交易所对账分开运行。部署时需先执行已注册的 `20261121_strategy_order_batches.sql` 迁移，再启动新版 worker。升级前已入队且没有批次标识的订单仍按原有逐笔方式处理，不追溯重新分组。

### 退出拒单与通知限频

Crypto 和其他券商不统一使用 `0.01` 数量阈值。现货尾仓按交易所的数量步长、最小数量和最小名义金额判断，并要求使用新鲜、未锁定且与策略归属一致的账户余额。规则缺失或余额不一致时，不认定为尾仓。被认定的尾仓仍保留数量和价值，并在后续对账时重新判断。

Strategy V2 对明确低于最小数量或最小金额而被拒绝的实盘退出请求，直接跳过数量未变化的重复请求。判断范围为同一用户、策略、凭证、交易通道、标的、市场类型及持仓方向。没有定时重试：重启策略、更新时间戳或退出原因、价格波动均不会使同一被拒数量重新入队；数量变化、部分成交或后续订单出现后按正常流程判断。持仓不会被舍入、删除或伪造成交。信号模式、开仓、原生零数量全平，以及余额、归属、认证、网络故障不受影响。单独的精度、`LOT_SIZE` 或 `invalid amount` 错误不能证明是小额尾仓，不会直接忽略。

上述数量类退出拒单首次正常通知，等价失败不再按时间重复发送，重启 worker 或策略也不会重新发送。通知去重由 PostgreSQL 原子操作协调；订单成功提交后重置此前失败通知，发送失败则释放本次通知名额，数据库异常时仍允许告警。所有失败记录继续保留供排查。

合约保留交易所的只减仓或原生全平路径，不会按开仓最小金额规则提前忽略持仓。港股碎股仍是真实持仓，不等于零价值尾仓；只有明确低于最小数量的拒单才跳过重复请求，本次不新增碎股交易通道，也不扩大实盘券商支持范围。已入队订单不会被取消。数量不变但后来已可交易的尾仓可能需要人工处理，本次不新增自动恢复服务。

## 可选的 JEV System One 开仓过滤

JEV 是一种 System One 模型：它针对整理好的状态与类型化问题输出结构化判断，而不是生成自由文本。普通实盘策略可在提交交易所前用它审核开仓订单；闪电交易使用确定性校验和用户明确确认，不接入 AI 决策过滤。策略过滤结果统一收敛为可审计的 `PASS` 或 `REJECT`；平仓、止损、止盈和紧急减仓会绕过过滤。JEV 不可用时系统降级到已配置的 LLM；两者均不可用时订单正常放行并记录服务不可用，避免 AI 故障中断交易。

## 大型股票池与行情排查

股票实盘的执行报价有效期可在“系统设置 → 实盘交易 → 报价最大允许延迟（分钟）”调整，对应 `EQUITY_QUOTE_MAX_AGE_MINUTES`，允许 1–60 的整数，默认 16 分钟。它同时适用于股票开仓、日线调仓、本地止盈止损和组合风控；股票接收缓存使用相同窗口，避免被加密货币的短超时提前拦截。保存后需重启交易及策略运行 Worker，无需数据库迁移。默认值兼容 15 分钟延迟行情，但不会使其变成实时行情；止损可能滞后，参考价也可能与成交价不同。仍检查原始行情时间、未来时间及当前连续交易时段；命中缓存不刷新原始时间。延迟源在开盘或午后开市初段仍可能等待本时段报价到达。加密货币、回测和仅通知模式的规则不变。

港股、美股日线运行预热以声明的有效 K 线数量为准：较新上市的股票即使不足预留的完整日历区间，只要已有足量、去重且 OHLC 有效的历史柱，也可以参与预热。这项例外只用于运行预热，历史回测仍检查请求区间。最新完成交易日、预热就绪以及执行报价的新鲜度检查继续生效；接口成功返回不代表 K 线已经更新。

日线运行请求按起始日期和已完成交易日统一缓存键，避免不同启动时间重复拉取同一段历史。每个 worker 的进程缓存最多保留 `STRATEGY_SHARED_FRAME_CACHE_MAX_SIZE` 条行情流（默认 4096），同时受 `STRATEGY_SHARED_FRAME_CACHE_MAX_BYTES` 限制（默认 256 MiB）。Redis 能否复用还取决于缓存配置和过期时间，这不是持久化历史行情库。加密货币和分钟、小时线的区间规则不变。

港股 K 线主源异常后继续尝试已有备用源。腾讯返回 HTTP 403、429、501 时，该进程暂避该源 60 秒，避免大型股票池逐只重复请求已被拦截的接口；已经发出的请求仍可能失败。备用源不生成虚假 K 线，这项容错也不保证公共数据源的可用性或付费源的授权覆盖。

日线实盘的 `Daily signal waiting for fresh quotes` 日志会列出缺失标的、来源和报价年龄，最多显示十项；恢复时单独记录。`Daily signal evaluated` 记录已计算的信号交易日和交易意图数量，包括零。意图数是提交券商前的数量，不代表成交。比较两个账户时，应同时核对源码、参数、完成日线和策略自有持仓：已有持仓可能继续配置资金，空仓却没有新的入场信号。需要更新策略 worker 后生效，无需数据库迁移。

## 币安 REST 请求协调

币安公共行情与账户 REST 共用限流器。标准 Compose 部署默认使用 jobs Redis；没有配置 Redis 的独立进程只在进程内协调。可用 `BINANCE_REST_REDIS_URL` 指定连接。共用出口 IP 的各进程、各部署应连接同一个 Redis 并使用相同 `BINANCE_REST_NAMESPACE`。已配置的协调服务不可用时暂缓请求，不退回无限请求；同 IP 上的其他程序不受本限流器管理。

行情/手续费查询与账户读取分开计数，每组默认共享每秒 5 次预算（`BINANCE_REST_READS_PER_SECOND`）。短拥塞最多等两秒，超过则返回可重试的限流错误，不发送 HTTP。这是保守的请求次数预算，不是完整的接口权重模型。响应 `X-MBX-USED-WEIGHT-1M` 达到 `BINANCE_REST_WEIGHT_SOFT_LIMIT`（默认 1800）时，读取暂缓至下一分钟。下单、撤单不占用读取预算；成功订单响应不会因记录权重失败而变成可重试错误，也不新增写请求自动重试。

收到 429/418 后，根据 `Retry-After` 和 `banned until` 取更长时间，所有币安 REST（包括写入）共享冷却；未提供时间时分别暂避 60/120 秒，另加一秒余量。实盘域名共用保守范围，模拟/测试域名单独计数。已有封禁仍须等待币安解除。手续费保持待补齐，不再按秒密集重试；K 线限流不会在同一交易所反复重试或误报币种不存在。合约执行先取对应账户的标记价格，缺失时才补普通行情。

更新代码或修改以上环境配置后，重启相关后端、行情及交易 Worker 生效，无需数据库迁移。此机制降低无效请求，不能保证交易所可用；报价或账户 REST 不可用时，不能据此保证本地止损能够执行。

## 异常处置

其他交易所的 REST 协调配置和官方文档链接见[交易所 REST 限流说明](EXCHANGE_REST_LIMITS.md#中文说明)。

1. 停止新的开仓和加仓。
2. 记录部署、账户、标的、订单 ID、时间和错误信息。
3. 对照交易所或券商的实际订单与持仓，不以页面缓存作为唯一依据。
4. 撤单或减仓前确认不会越过受保护的手工仓位。
5. 风险继续扩大时停止策略或执行紧急停止。
6. 根因和账本核对完成前不要重新启动。
